# 場景修整與實景驗證

適用於參考圖場景搭建與已存在場景的視覺修整。選擇本輪受影響的項目執行，不因本文件列出多種問題就重建全部資產。

## 參考對照先於裝飾

建立區域對照表：參考地標、預期位置／相鄰關係、高低差、進出道路、模型來源、目前差距、驗證畫面。圖片底部的資產表用來盤點模組，整張場景圖用來決定組裝；兩者不能互相取代。

在投入細節前，比對以下尺度：

- 同一投影／相近朝向下的全景：輪廓、建築佔地、廣場留白、河道與崖壁層次。
- 玩家鏡頭：角色相對門窗、橋寬、樓梯與 NPC 入口的大小；不要只在遠距總覽隱藏問題。
- 地標近景：屋身材質、木構、石井、礦口、船殼及水體。若參考有上下游兩座橋，就分別檢查兩座橋，不能只測其中一座。

若玩法所需公會、通道寬度或鏡頭與概念圖不同，記錄具體理由與偏差。未經人工認可時，報告只描述已完成的搭建與可觀察差距。

## 可重複的 Blender 修整

保留完整可編輯主檔，以分區 Collections 管理地形、道路、建築、植栽、水體、道具與碰撞來源。修整函式只管理自身命名的物件，重跑不疊加；固定需要重現的隨機種子，記錄腳本／layout／輸出檔 SHA。

生成模型有黑斑、融合雜物或破屋頂時，先定位不合格表面。可保留合格屋頂與既有擺放，將缺陷立面替換為閉合牆、木框、門窗及石基；不要把所有原模型一律減面或改色。保留原始來源及修改範圍，使用共用材質，記錄實際使用的表面而非只檢查檔名。

純美術修整可先保存 Terrain／Paths／Bounds 的世界座標頂點、面及 transform 雜湊，並記錄入口、NPC、出生點。若新參考要求改路或高低差，走正常 layout 版本與遷移流程，不強行凍結不合格舊布局。

CLI 範例；程式路徑與參數採專案實際入口：

```powershell
& $blenderPath --background --factory-startup --python-exit-code 1 --python $builderScript
```

在獨立背景程序使用 factory-startup；不在使用者 live session 重置場景。確認 Python 退出碼、完成 marker、輸出時間及雜湊後再匯入。MCP 即時預覽若另用 GLB 載入，標明它對應的主檔版本與材質差異。

## 常見缺陷與驗證方法

| 缺陷 | 修整方向 | 有意義的驗證 |
|---|---|---|
| 樓梯旁破洞、草皮懸空 | 補實體岩肩／地面接合，檢查法線及非退化面 | 三角網格射線／支撐點與玩家近景；不能只關閉背面剔除 |
| 樹、岩石或花圃侵入路面 | 以碰撞體、角色半徑、頭部高度及 NPC 活動空間留淨空 | 實際走跑上下階與轉折，兩橋分別檢查；小裝飾沒有碰撞仍可能視覺擋路 |
| 生成屋身黑斑／融合物件 | 局部替換為清楚、閉合、可重用的建築表面 | 牆面／屋頂取樣、使用中的材質與近景；測門窗凸出是否超出既有碰撞容許範圍 |
| 船底穿水／船殼缺面 | 補閉合厚度，調整吃水與內底高度 | 若採封閉船殼，檢查三角邊鄰接；內底／水線幾何檢查加實景 |
| 匯入後石材或木材變白 | glTF 支援的材質／烘焙貼圖，或 Godot 等效共享 Shader | 查看真正 Mesh surface 與 override；Blender 畫面不能證明 Godot 材質正確 |
| 瀑布穿崖／拼接斷裂 | 沿地形建立連續曲面、統一流向 UV | 對實際崖壁三角形做 BVH／射線間距採樣，檢查上游、崖口與落水區 |

採樣只覆蓋被採樣的位置；記錄範圍，不把射線數量當作全場景無缺陷的保證。

## 水體、紋理與預算

- 水流沿曲面弧長配置 UV，分開處理河面、落水、水沫及河石尾流。匯入後確認上游／落水端的實際 UV 與動態方向；依觀察處理 Blender→glTF 的 V 轉換，不對所有資產一律翻轉 V。
- 流動幾何對實際崖壁留間距。新河石與浪花不進入橋面可走體積，裝飾不新增密集碰撞。
- 先考慮共享材質、批次網格及少量不透明／裁切水沫，再按效果需求增加透明或粒子；不能為省成本令效果不可見。
- 固定鏡頭截取相隔已知時間的兩幀，查看流向與落水效果。必要時比較水面區域與靜態岩壁區域的像素變化，辨別真正動畫與鏡頭／光影變化。這不等於流體物理或流向已自動證明。
- 大面積土路／草地可用材質分區收邊，但保留獨立道路的可見寬度與連通性。不要用 Shader 把本來可走的路隱藏得不可辨識。
- 記錄可見三角面、Mesh／surface、Draw Calls 及記憶體；將隱藏碰撞網格分開統計。幾何合併須保留可替換分區，避免修改共用 Mesh 意外影響其他實例。

## 回歸與證據

先載入／匯入，再在圖形模式操作真正的 CharacterBody3D 與 InputMap：主要路線、上下階、轉向、走跑、邊界與入口。純數值碰撞、瞬移到端點或無頭測試不能替代探索動線。

接著依影響範圍驗證 NPC、商店／旅館、序章戰鬥、回村交付、單次獎勵、舊檔遷移及獨立程序重啟。沿用既有 Manager 與測試入口，不另造測試專用 RPG 邏輯。

截圖前等物理步進與相機穩定，再等 frame_post_draw。保存全景、玩家視角、關鍵近景及重現失敗的畫面；逐張檢視，不以輸出檔存在代替視覺審查。留記錄說明哪個缺陷已修正，哪些仍未通過。

效能證據註明引擎版本、硬體、render backend、幀率上限、樣本時長／數量與監測口徑。frame_post_draw 間隔不是 GPU 耗時；引擎記憶體、程序 RSS、顯存各自記錄。短取樣不外推成長時間穩定性或手機效能。

灰石村可重用入口（專案根目錄相對路徑，先確認仍適用）：

- `scripts/tools/greystone/audit_reference_facades.py`、`reference_v5_preview.gd`：幾何／原生通行驗證。
- `scripts/world/reference_village_surfaces.gd`：Godot 材質接入。
- `tools/godot.ps1` 的 `Check`、`TestReferenceVillage`、`VisualReferenceStory`、`VisualReferenceCommerce`、遷移／重啟及 `CaptureReferenceVillage`：依工具實際 ValidateSet 選模式。
