# 開發執行流程

## 每次任務

1. **確認基線**：讀 AGENTS、TASKS、相關設計及最近變更；故事工作另讀 STORY_IMPLEMENTATION，按需查 STORY_BIBLE；檢查使用者修改、目前階段、Godot 版本。
2. **選最小工作項**：每次一個能驗收的行為；記下預期、影響的檔案和驗證方式。已獲使用者授權的範圍直接執行。
3. **實作**：先佔位場景和核心行為，再串接資料/UI；不把後續階段系統提前塞進本階段。
4. **機器檢查**：有專案後執行 Check；有 Main 後執行 Smoke；資料/戰鬥/存檔改動執行適合的行為測試。檢查退出碼和錯誤輸出。
5. **遊戲驗收**：依 ACCEPTANCE 實際操作；涉及畫面時查看截圖或實際視窗。沒有操作或畫面證據就保留待驗收。
6. **回歸**：測受影響的既有功能；跨系統改動重走探索→戰鬥→返回→保存/讀取的已實作部分。
7. **紀錄及交付**：更新 TASKS、CHANGELOG、驗收結果。說明做了什麼、測了什麼、缺什麼，並保留可重現指令。

只有流程文件時，驗證文件連結、指令可用性、工具腳本語法與錯誤處理，不宣稱遊戲載入已通過。

## 故事內容進入流程

Story Bible 是內容來源，STORY_IMPLEMENTATION 是範圍/衝突/資料契約紀錄，TASKS 是開發狀態。新增故事依「保留原文 → 核對角色/章節/ID → 更新資料及差異紀錄 → 排入對應階段 → 實作 → 驗收」處理。資料檔通過 JSON 解析只代表可讀，不能標記劇情可玩。

原文六項故事工作分配為：Story System/Dialogue UI/Quest 最小版於 P2，Battle Integration 於 P3，入隊與獎勵於 P4，Save/Load 與 Full Prologue 於 P5，匯出與完整體驗於 P6。P1 維持原本骨架範圍。跨階段依賴未就緒時只測已實作範圍，禁止假裝戰鬥勝利或靜默跳過動作。

每次劇情資料改動核對事件前置旗標、觸發位置、勝利等待、任務顯示與獎勵來源；涉及已發布 ID/Flag 要加存檔遷移。序章通過後才依第一章至終章增加地區、艾琳、角色支線及結局，不一次開發 12～16 小時內容。

## 任務狀態

| 狀態 | 意義 |
| --- | --- |
| 待開始 | 尚未實作；勾選框不打勾 |
| 進行中 | 已開始但仍有未完成項目 |
| 待驗收 | 實作和可執行檢查完成，還有操作或畫面驗收未做 |
| 完成 | 本項全部驗收條件都有證據 |
| 受阻 | 明確外部條件阻擋，記錄原因與可繼續的其他項目 |

階段依 P1 → P2 → P3 → P4 → P5 → P6。當階段仍有解析錯誤、崩潰、功能失敗或資料遺失，不進入下一階段。若缺少人工或圖形驗收則標記待驗收，不自行填通過；這不是要求每個小改動重新徵求許可。

## 版本控制與回復

已初始化本地 Git（main），不建立遠端或推送。每個通過驗收的小項保留可辨識的本地提交/檢查點，先檢查 diff；失敗修復僅針對自己的變更，禁止用 reset/clean 清掉使用者檔案。

## 美術與發佈

P1～P3：基本幾何體 → 確認玩法尺度及碰撞 → 記錄正式資產需求。

使用者已允許取用素材商店資產並修改。先核對與本專案的風格/授權適合程度，下載後保留授權與來源，記錄到 ASSET_CREDITS；先以單一資產驗證比例、碰撞、材質與匯入，再擴充。未經購買授權不支出費用；本輪未下載第三方素材。

P6：原創/有授權的模型 → Blender 修整、比例/朝向/骨架/動畫檢查 → GLB 匯入 → 碰撞與材質檢查 → 遊戲內畫面及效能驗收。每份外部資產記來源、授權及修改內容，原始檔保留在 source_assets。

Windows 匯出需核對匹配的 export templates；產物在 builds，不只測編輯器。用匯出版本走一次完整 20～30 分鐘序章（含回村 E008），測保存/讀取與重啟。第一章解鎖只要求旗標與預告，不表示第一章地圖已存在。發佈到外部平台另依使用者要求執行。
